intune-{{ $fullname }}-0 ({{ .Values.broker.embedded.persistence.size }}). The logs show it, and the app says "Setting up the Intune
container…" meanwhile ("Starting the Intune container…" on a later boot).
{{- if .Values.broker.embedded.import.secretName }}
It then imports the enrollment backup in Secret {{ .Values.broker.embedded.import.secretName }} (key {{ .Values.broker.embedded.import.key }}) — once,
while this pod's state holds no device registration. STOP that enrollment on the machine it came
from: this is a MOVE, and two live copies of one device are unmeasured. Once it is imported, drop
the Secret — the import's own upgrade, pinned to the chart version this release runs

It boots only on a node whose kernel permits unprivileged user namespaces. On Ubuntu 23.10 and
later (24.04 LTS included) that means kernel.apparmor_restrict_unprivileged_userns=0, set ON THE
NODE: while it is 1 the Intune container refuses to start, privileged or not, and the logs say
"AppArmor restricts unprivileged user namespaces". A pod cannot set it (it is not a namespaced
sysctl), and an AppArmor profile does not get past that check.
{{- if .Values.broker.embedded.userNamespaces }}

UNVERIFIED — pod user namespaces (broker.embedded.userNamespaces) instead of a privileged
container. Nothing about this shape has been run. It needs containerd 2.1 or later with writable
cgroups, the UserNamespacesSupport and ProcMountType feature gates, volumes that support idmapped
mounts, the kubelet's userNamespaces.idsPerPod at 196608 or more (uid 1000 and the 65536
subordinate ids from 100000), and a seccomp profile allowing unshare, mount and setns.
{{- else }}

It runs PRIVILEGED: it boots a whole Intune container inside itself.
{{- end }}
A namespace enforcing the `baseline` or `restricted` Pod Security level refuses it — label this one
`pod-security.kubernetes.io/enforce=privileged`.

Its Intune state (the claim above) is kept by `helm uninstall`: it is the device's enrollment.
A locked Intune keyring is repaired by the pod itself, and the sign-in window is served into the
app — both without hostNetwork, which this mode refuses.
{{- if .Values.broker.embedded.vmIsolated }}

DECLARED — a microVM runtime (broker.embedded.vmIsolated): the entrypoint lets this pod boot in
the kernel's INITIAL network namespace on that word alone (TEAMS_LITE_NETNS_IS_OWN=1), because
under Kata Containers or Firecracker that namespace is the guest kernel's, the sandbox's own.
Nothing in the pod can check it. On a pod that shares the node's kernel the same namespace IS the
node's network — hostNetwork by another name — and the Intune container would take the :99 of
one already running there: set it only where the pod runs in a VM of its own. The chart does not
choose that runtime, and no microVM runtime has run this image (UNVERIFIED).
{{- end }}
{{- else if $embedded }}

It keeps the claim intune-{{ $fullname }}-0 all the same, mounted read-only, so turning readOnly off
later is a `helm upgrade` (a StatefulSet cannot change its claims in place), and `helm uninstall`
keeps it. It runs UNPRIVILEGED — privilege is what booting an Intune container costs, and this
release boots nothing — with only the capabilities its entrypoint uses as root: to take over a
fresh store claim's root (the backend creates its store there), to drop to the image's user, and
to pass that user the stop signal. By the Pod Security Standards that is
`baseline`; `restricted` refuses it, since it starts as root and drops itself.
